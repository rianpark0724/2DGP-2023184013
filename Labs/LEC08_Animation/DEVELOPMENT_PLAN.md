# Drill #8 애니메이션 뷰어 개발 계획

작성일: 2026-09-29  
기술: Python + pico2d  
최종 실행 파일: `LEC08/animation_viewer.py`  
목표: 필수 요구사항 전체 + 선택 과제 2종 전체 + 의미 있는 커밋 20개 이상

> 이 문서는 구현 전 개발 계획이다. 아직 프로그램 구현·실행 검증·Git 커밋을 완료한 상태가 아니다. 실제 개발은 아래 순서대로 기능을 추가하고 확인한 뒤 커밋한다.

## 1. 과제 해석과 완성 목표

첨부한 과제 안내 이미지와 레이무 스프라이트 시트를 기준으로, 화면 중앙에서 여러 동작을 자동으로 보여 주는 애니메이션 뷰어를 만든다. 게임 조작, 전투, 충돌 처리는 개발 범위에 넣지 않는다.

### 요구사항과 검증 기준

| 구분 | 과제 요구사항 | 구현 계획 | 완료 판단 |
| --- | --- | --- | --- |
| 필수 | 스프라이트 시트로 캐릭터 애니메이션 구현 | 첨부 레이무 시트에서 동작별 프레임을 추출해 순서대로 표시 | 원본 시트의 동작이 연속적으로 재생됨 |
| 필수 | 최소 4종 이상 | 시각적으로 구분되는 4개 동작을 선정 | 서로 다른 4종이 자동 순환함 |
| 필수 | 작은 캐릭터 확대, 적어도 화면 절반 정도 | 캐릭터 본체의 대표 높이를 창 높이의 약 50~60%로 확대 | 배경 여백을 제외한 본체 크기를 화면에서 확인 |
| 필수 | `LEC08/animation_viewer.py` | 해당 경로를 실행 진입점으로 유지 | 지정 경로와 파일명으로 실행 가능 |
| 필수 | 화면 중앙에서 재생 | 공통 기준점과 프레임별 보정값으로 중앙 정렬 | 프레임 전환 시 캐릭터가 불필요하게 흔들리지 않음 |
| 필수 | 각 애니메이션 5회 반복 | 마지막 프레임의 표시 시간이 끝날 때 반복 횟수 증가 | 정확히 5회의 완전한 동작을 확인 |
| 필수 | 5회 반복 후 1초 정지 | 마지막 프레임을 유지하는 대기 상태 | 약 1초 뒤 다음 동작으로 전환 |
| 필수 | 모든 애니메이션을 차례로 무한 반복 | 마지막 동작의 대기 종료 후 첫 동작으로 복귀 | 전체 순서가 2회 이상 연속 순환함 |
| 선택 +2점 | 프레임마다 크기가 다른 복잡한 시트 | 프레임별 독립적인 잘라내기 영역과 기준점 지원 | 실제로 폭·높이가 다른 프레임이 정상 재생됨 |
| 선택 +2점 | 애니메이션마다 다른 프레임 수 | 각 동작의 실제 프레임 목록 길이로 재생 | 실제 프레임 수가 서로 다른 동작이 정상 순환함 |
| 제출 조건 | 충분히 작성한 커밋 로그 20개 이상 | 목표 30개, 변경 이유·내용·검증 결과 기록 | 최종 제출 이력에 의미 있는 커밋 20개 이상 존재 |

과제 안내의 기본 배점은 정확한 재생 2점, 확대 1점, 무한 반복 1점이며 선택 과제는 각각 +2점이다. 두 선택 기능은 구현뿐 아니라 **제출 설명에서도 명시**한다. 안내문은 커밋 조건 미충족 시 점수 인정 자체가 되지 않을 수 있다고 강조하므로, 커밋 기록을 개발 과정의 필수 산출물로 관리한다.

화면 절반이라는 표현은 구체적인 치수 기준이 없으므로, 계획에서는 **창 높이에 대한 캐릭터 본체 높이**로 해석한다. 실제 수업에서 다른 기준을 안내했다면 그 기준을 우선 적용한다.

## 2. 첨부 자료 분석과 동작 선정

### 확인한 자료

| 자료 | 확인 내용 | 활용 |
| --- | --- | --- |
| `F6QXIY7GOZYZE.png` | 1673×853 크기의 과제 안내 이미지 | 요구사항과 제출 점검 기준 |
| `PC _ Computer - Touhou Shinkirou (Hopeless Masquerade) - Playable Characters (Trial Ver.) - Reimu Hakurei (Trial Ver.).png` | 899×2048, RGBA 형식이며 투명도 채널 존재 | 실제 애니메이션 원본 |

시트에는 자세·무기·이펙트의 범위가 서로 다른 많은 프레임이 보인다. 전체 이미지를 같은 크기의 격자로 균등 분할하는 방식은 사용하지 않는다. 화면에서 검게 보이는 영역을 곧바로 불투명 배경으로 판단하지 않고 투명도 채널을 확인한다.

### 초기 동작 후보

| 순서 | 후보 이름 | 선정 기준 |
| --- | --- | --- |
| A | 대기/부유 | 반복 연결이 자연스럽고 기준 자세를 잡기 쉬운 구간 |
| B | 이동/비행 | 몸의 방향이나 기울기가 A와 뚜렷이 다른 구간 |
| C | 일반 공격 | 준비·공격·회수 과정이 구분되는 구간 |
| D | 회전/특수 공격 | 자세나 이펙트 변화가 크고 C와 구분되는 구간 |

위 이름은 **육안 분석을 위한 임시 이름**이다. 원작의 정확한 기술명, 각 구간의 경계, 프레임 좌표와 개수는 아직 확정하지 않았다. 과제에 적힌 걷기·뛰기·점프·공격은 예시이므로, 시트에 실제 존재하는 서로 다른 동작 4개를 우선한다.

선정 절차는 다음과 같다.

1. 시트를 확대해 행과 동작 경계를 확인한다. 한 행 전체가 반드시 한 애니메이션이라고 가정하지 않는다.
2. 후보마다 시작·끝·재생 순서를 기록한다. 분리된 무기나 이펙트를 해당 캐릭터 프레임에 포함한다.
3. 후보 프레임을 하나씩 확인하고 임시 재생해 잘림과 순서 오류를 찾는다.
4. 실제 프레임 수가 서로 다른 동작을 최소 2개 포함하도록 4종을 확정한다. 프레임을 임의로 삭제하거나 복제해서 차이를 만들지 않는다.
5. 프레임별 폭·높이 차이가 실제로 존재하는 구간을 포함해 첫 번째 선택 과제를 증명한다.

단순한 연결 영역 자동 검출만으로 확정하지 않는다. 부유하는 무기·장식·이펙트가 캐릭터 본체와 떨어져 있을 수 있고 인접 동작을 잘못 합칠 수 있으므로, 최종 프레임 영역은 사람이 확인한다.

### 책임 구분

- **자료 읽기:** 파일 존재 여부와 프레임 데이터 유효성 검사, 이미지 한 번 불러오기.
- **재생 제어:** 현재 동작, 프레임, 반복 횟수, 경과 시간, 재생/대기 상태 관리.
- **화면 표시:** 현재 프레임 잘라내기, 확대, 정렬, 배경과 상태 표시.
- **이벤트 처리:** 창 닫기와 Escape 종료. 대기 중에도 입력을 계속 처리.

런타임은 Python 표준 라이브러리와 pico2d를 기본으로 한다. 별도 게임 엔진이나 웹 UI는 추가하지 않는다. pico2d 버전은 수업 환경을 먼저 확인하고, 실제 실행된 버전을 기록한다. 현재 배포 정보의 확인 경로는 [pico2d PyPI](https://pypi.org/project/pico2d/)이며 최신 버전을 무조건 채택하는 것은 아니다.

## 4. 프레임 데이터와 가변 크기 지원

### 프레임별 기록 항목

| 항목 | 의미 |
| --- | --- |
| 프레임 식별자 | 어떤 동작의 몇 번째 프레임인지 구분 |
| 왼쪽 좌표와 위쪽 좌표 | 원본 시트에서 잘라낼 시작 위치 |
| 폭과 높이 | 프레임마다 독립적으로 지정하는 실제 영역 |
| 기준점 좌표 | 해당 영역 안의 몸통 등 캐릭터 정렬 기준 |

### 애니메이션별 기록 항목

| 항목 | 의미 |
| --- | --- |
| 식별자와 표시 이름 | 동작 구분과 현재 동작 안내 |
| 순서가 있는 프레임 목록 | 재생 순서와 실제 프레임 수 |
| 재생 속도 | 초당 프레임 수; 초기에는 약 8~12 범위에서 육안 조정 |

모든 동작이 같은 프레임 수를 공유하도록 만들지 않는다. 한 동작의 끝은 그 동작의 프레임 목록 길이로 판단한다. 최종 문서에는 A·B·C·D의 실제 프레임 수를 적고, 크기가 다른 프레임의 구체적인 예도 남긴다.

이미지 편집 기준 좌표는 좌상단 원점으로 통일한다. 렌더링에 필요한 좌표 체계와 차이가 있으면 잘라내기 단계에서만 변환한다. 좌하단 원점을 사용하는 호출에서는 원본 높이에서 위쪽 좌표와 프레임 높이를 빼는 방식으로 아래쪽 좌표를 구한다. 실제 설치한 pico2d의 잘라내기 동작을 단일 프레임으로 먼저 확인한다.

데이터를 읽을 때는 양수인 폭·높이, 시트 경계 안의 영역, 비어 있지 않은 프레임 목록, 양수인 재생 속도를 검사한다. 잘못된 값이 있으면 동작 이름과 프레임 번호를 포함해 원인을 알려 준다.

## 5. 확대와 중앙 정렬

- 초기 창 크기는 **800×600**을 제안한다. 최종 크기는 실제 프레임의 범위를 보고 확정한다.
- 본체의 대표 높이를 약 **300~360픽셀**로 보이게 조정한다. 이펙트까지 포함한 프레임 사각형의 높이만으로 확대 충족을 판단하지 않는다.
- 가로·세로에 동일한 확대 배율을 적용해 비율을 유지한다.
- 서로 다른 크기의 프레임을 같은 출력 폭·높이에 억지로 맞추지 않는다. 각 프레임의 폭·높이에 공통 배율을 곱해 표시한다.
- 캐릭터 몸통 근처의 공통 기준점을 화면 중앙에 둔다. 각 프레임의 사각형 중심과 기준점 사이의 차이를 확대 배율만큼 보정한다.
- 프레임마다 자동 배율을 다시 계산하지 않는다. 프레임이 바뀔 때 캐릭터가 커졌다 작아지는 현상을 방지한다.
- 의도된 몸동작은 보존하고, 잘라낸 영역의 여백 차이 때문에 생기는 위치 흔들림만 보정한다.

4개 동작을 고른 뒤 모든 프레임의 기준점 기준 상하좌우 최대 범위를 계산해 이펙트가 화면 밖으로 나가는지 확인한다. 큰 이펙트 때문에 본체 확대와 화면 내부 표시를 동시에 만족하지 못하면, 동작 후보나 창의 가로세로 구성을 먼저 조정한다. 최종 화면에서는 본체 크기와 가장 넓은 공격 프레임을 함께 검증한다.

## 6. 재생 규칙과 시간 처리

### 기본 동작

1. A의 첫 프레임부터 재생한다.
2. A의 마지막 프레임까지 정상 표시하면 1회 완료로 센다.
3. 1~4회 완료 시 A의 첫 프레임으로 돌아간다. 반복 사이에는 별도 정지가 없다.
4. 5회 완료 시 마지막 프레임을 유지하며 1초 대기한다.
5. B의 첫 프레임부터 같은 규칙을 적용한다.
6. C, D에도 적용하고, D의 1초 대기가 끝나면 A로 돌아간다.

### 상태별 동작

| 현재 상태 | 화면과 처리 | 전환 조건 |
| --- | --- | --- |
| 재생 중 | 현재 프레임 표시, 누적 시간으로 다음 프레임 계산 | 5회 완주하면 대기 상태 |
| 대기 중 | 직전 동작의 마지막 프레임 유지, 이벤트 처리 계속 | 1초 경과 시 다음 동작의 재생 상태 |
| 종료 | 반복 종료와 자원 정리 | 창 닫기 또는 Escape |

프레임 수가 N, 재생 속도가 F일 때 한 동작의 예상 소요 시간은 **5 × N ÷ F + 1초**다. 속도가 일정하지 않은 별도 프레임 시간 기능은 현재 범위에 넣지 않는다.

화면 갱신 횟수에 따라 애니메이션 속도가 달라지지 않도록 실제 경과 시간을 누적한다. 1초 대기를 긴 정지 호출로 구현하지 않는다. 마지막 프레임도 지정된 표시 시간을 모두 가진 뒤 반복을 완료하고, 5번째 완주 뒤에만 대기를 시작한다.

일반적인 일시 지연에서는 누적된 시간을 보존해 경계를 순서대로 처리한다. 디버거 중단 등으로 매우 큰 시간 차이가 생기는 경우의 처리 정책은 구현 시 명시하고, 한 갱신에서 여러 경계를 통과해도 반복 횟수가 5를 넘거나 대기 상태를 누락하지 않는지 검증한다.

## 7. 점진적 개발과 30개 커밋 계획

**한 번에 완성한 뒤 커밋만 잘게 나누지 않는다.** 아래 각 단계에서 변경 → 실행 또는 데이터 확인 → 결과 기록 → 커밋을 수행한다. 아직 구현하지 않은 기능을 완료했다고 기록하지 않는다. 불필요한 공백 변경, 동일 파일 재저장, 빈 커밋은 개수 확보에 사용하지 않는다.

커밋 메시지의 제목은 아래 예시를 사용하되, 본문에는 변경 이유·실제 변경·검증 결과를 짧게 작성한다. 문서만 바꾼 경우에는 실행 테스트 대신 검토한 내용을 적는다.

### 작업을 나눠 진행할 때의 기준

- 1차: 01~07, 실행 창과 캐릭터 한 프레임까지.
- 2차: 08~15, 데이터 기반의 첫 동작과 가변 크기 지원까지.
- 3차: 16~24, 4종·5회·1초·무한 반복까지.
- 4차: 25~30, 검증과 제출 설명까지.

각 차수 시작 시 이전 실행 상태와 마지막 커밋을 확인한다. 종료 시 완료 번호, 실제 커밋 해시, 검증 결과, 다음 할 일을 남긴다. 기존 수업 저장소가 있다면 그 저장소의 이력과 구조를 유지하고 LEC08 범위에서 진행한다. 제출 전에 커밋을 하나로 합치거나 이력을 재작성해 20개 미만으로 만들지 않는다. 파일 업로드만으로 Git 이력이 전달된다고 가정하지 않고 수업의 저장소 제출 방식도 확인한다.

## 8. 핵심 검증 시나리오

| 시나리오 | 확인 방법 | 기대 결과 |
| --- | --- | --- |
| 원본 영역 | 각 동작의 처음·중간·끝을 개별 표시 | 이웃 캐릭터가 섞이지 않고 무기·장식 보존 |

| 다른 프레임 수 | 확정한 A~D의 실제 개수를 기록하고 연속 전환 | 각 동작이 자신의 마지막 프레임까지 재생 |

| 1초 대기 | 대기 진입·종료의 경과 시간 기록 | 일반 실행에서 1초에 화면 갱신 오차를 더한 수준 |
| 마지막 프레임 | 5회차 마지막 프레임의 표시 시간 확인 | 마지막 프레임 생략 없이 1초 정지로 이어짐 |
| 무한 순환 | 최소 두 바퀴 및 최소 3분 실행 | A→B→C→D 순서를 계속 유지 |
| 확대·중앙 | 창과 본체 높이, 기준점, 최대 이펙트 범위 확인 | 절반 정도 크기, 비율 유지, 화면 잘림 없음 |
| 일시 지연 | 경과 시간이 여러 프레임 간격을 넘는 경우 검사 | 잘못된 반복 횟수·동작 순서·대기 누락 없음 |
| 대기 중 종료 | 1초 정지 구간에서 종료 입력 | 입력에 응답하고 정상 종료 |
| 자료 누락 | 개발 중 잘못된 경로·영역을 별도 확인 | 원인을 알 수 있는 오류 안내 |
| 실행 위치 | 저장소 루트와 LEC08에서 실행 | 동일한 자료를 찾아 정상 동작 |

검증은 완료 여부만 체크하지 않고 **실제 동작명, 프레임 개수, 사용한 환경, 관찰한 결과**를 기록한다. 현재 문서의 체크 항목은 모두 앞으로 수행할 계획이며 실행 결과가 아니다.
